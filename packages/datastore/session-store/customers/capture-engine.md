# Customer: packages/lib/capture-engine

Capture-engine is a customer of session-store for writing chunks during recording.

## Producer's Understanding of This Customer

**Identity**: Capture-engine is a lib package that captures live audio from the microphone, encodes PCM to MP3 chunks every ~4 seconds, and writes those chunks to durable storage immediately during recording.

**Core need**: Fast, reliable chunk writes during active recording. Capture-engine needs session-store to persist chunks to IndexedDB as they encode (every ~4s), without blocking the audio capture thread. Write failures (session not found, quota exceeded) must be returned as errors (not thrown exceptions) so capture-engine can emit `captureError` events to the PWA and handle gracefully.

**When capture-engine calls session-store**:
- **During recording** (every ~4s): capture-engine encodes PCM → produces MP3 chunk blob → calls `writeChunk(sessionId, chunkData)` → session-store validates sessionId exists → writes chunk to IndexedDB → updates session metadata (chunkCount, sizeBytes, duration) → returns chunkId or error
- **On recording stop** (once): capture-engine flushes remaining PCM buffer → encodes final chunk (< 4s duration) → calls `writeChunk(sessionId, finalChunkData)` → session-store writes final chunk → returns chunkId or error

**Inputs capture-engine will provide to writeChunk**:
- `sessionId: string` (provided by PWA when PWA calls capture-engine's `startCapture(sessionId)`)
- `chunkData: {seq: number, startTime: number, endTime: number, duration: number, blob: Blob, sizeBytes: number}`
  - `seq`: sequential chunk number (0, 1, 2, 3... monotonic but may skip if encoding fails)
  - `startTime`: chunk start time in seconds (from PCM sample count, NOT wall clock)
  - `endTime`: chunk end time in seconds (from PCM sample count)
  - `duration`: chunk duration in seconds (endTime - startTime, typically ~4s, final chunk may be < 4s)
  - `blob`: MP3 encoded audio blob (binary data)
  - `sizeBytes`: blob.size in bytes

**Outputs capture-engine expects from writeChunk**:
- **Success**: `{chunkId: string}` (unique chunk ID generated by session-store)
- **Failure**: Error object (NOT thrown exception), one of:
  - `{error: "session_not_found"}` → capture-engine emits `captureError(sessionId, "session_not_found")` event, stops capture
  - `{error: "quota_exceeded", usedBytes: number, capBytes: number}` → capture-engine emits `captureError(sessionId, "quota_exceeded")` event, stops capture (caller/PWA can then call enforceRetentionPolicy to reclaim space)
  - `{error: "database_unavailable"}` → capture-engine emits `captureError(sessionId, "database_unavailable")` event, stops capture

**Error handling expectations**:

Capture-engine will NOT crash if writeChunk fails. It will:
1. Check writeChunk return value for error field
2. If error exists → emit `captureError(sessionId, error.error)` event to PWA
3. Stop capture gracefully (do not attempt to write more chunks)
4. Mark capture as "completed without playable audio" if no chunks were successfully written (watchdog timeout scenario)

Session-store must:
- Return error objects (NOT throw exceptions)
- Validate sessionId exists BEFORE writing chunk (call getSession(sessionId), if null → return `{error: "session_not_found"}`)
- Check quota before writing chunk (if usedBytes + chunkData.sizeBytes > capBytes → return `{error: "quota_exceeded", usedBytes, capBytes}`)
- Handle IndexedDB failures gracefully (if IndexedDB write fails → return `{error: "database_unavailable"}`)

**Referential integrity requirements**:

Capture-engine will NOT create sessions itself. PWA creates session via `createSession()`, passes session ID to capture-engine's `startCapture(sessionId)`. Capture-engine assumes session exists when it starts writing chunks.

Session-store MUST validate sessionId exists before writing chunk. If sessionId does not exist (e.g., session was deleted between createSession and first writeChunk, or sessionId is invalid), return `{error: "session_not_found"}`.

**Sequential write behavior**:

Capture-engine writes chunks sequentially during recording:
- First chunk: seq=0, startTime=0.00s, endTime=~4.12s (varies based on PCM samples captured)
- Second chunk: seq=1, startTime=~4.12s, endTime=~8.24s
- Third chunk: seq=2, startTime=~8.24s, endTime=~12.36s
- ...
- Final chunk: seq=N, startTime=~(N*4)s, endTime=~(N*4 + remainder)s, duration < 4s if recording stopped mid-encode

Chunk seq numbers are monotonic (0, 1, 2, 3...) but may not be strict 0-1-2 if an encoding operation fails (e.g., seq=0, seq=1, seq=3 if seq=2 encoding failed). Session-store does NOT need to enforce strict sequential seq (gaps are allowed).

**Session metadata updates**:

When writeChunk succeeds, session-store MUST update session metadata:
- `session.chunkCount += 1` (increment chunk count)
- `session.sizeBytes += chunkData.sizeBytes` (accumulate total session size)
- `session.duration = max(session.duration, chunkData.endTime)` (update session duration to latest chunk end time)
- `session.updatedAt = now` (update last modified timestamp)

Capture-engine relies on these metadata updates to emit accurate `chunkEncoded(sessionId, chunkId, duration)` events to PWA. PWA displays session duration and size in session list UI.

**Performance expectations**:

WriteChunk must be fast enough to not block audio capture. Typical target: < 50ms per writeChunk call. Capture-engine calls writeChunk from a Web Worker (not main thread), so IndexedDB write latency is acceptable as long as it does not cause PCM buffer overflow.

If writeChunk takes > 500ms (e.g., slow IndexedDB on constrained device), capture-engine may accumulate multiple encoded chunks in memory before calling writeChunk sequentially. Session-store does not need to handle concurrent writeChunk calls for the same sessionId (capture-engine serializes writes).

**What capture-engine does NOT need from session-store**:

- Does NOT need session creation (PWA does that)
- Does NOT need session listing/reading (PWA does that)
- Does NOT need volume profile writes (volume-analyzer does that)
- Does NOT need snip writes (volume-analyzer does that)
- Does NOT need transcript writes (PWA does that)
- Does NOT need session deletion (PWA does that)
- Does NOT need retention policy enforcement (PWA does that)

**Summary**: Capture-engine is a high-frequency writer customer during recording. It needs fast, reliable `writeChunk` with error returns (not exceptions), referential integrity validation (sessionId must exist), quota checking (quota_exceeded error before write), and automatic session metadata updates (chunkCount, sizeBytes, duration). Session-store must handle writeChunk failures gracefully and return error objects so capture-engine can emit `captureError` events and stop capture cleanly.

## Customer Request

I'm capture-engine. I need session-store to persist MP3 chunks to IndexedDB during active recording (every ~4 seconds). Chunk writes are my only connection to durable storage. If writes fail, recording fails. Here's what I need:

### Core Interface I Need

**`writeChunk(sessionId, chunkData)`** (called every ~4s during recording)

When I call it: Every time I encode a complete PCM buffer to MP3 (approximately every 4 seconds), plus once more on recording stop for the final partial chunk

Input: 
- `sessionId: string` (from PWA, passed to my `startCapture(sessionId)` call)
- `chunkData: {seq: number, startTime: number, endTime: number, duration: number, blob: Blob, sizeBytes: number}`
  - `seq`: Sequential chunk number (0, 1, 2, 3...). Monotonic but may have gaps if encoding fails (e.g., 0, 1, 3). I do NOT guarantee strict sequential ordering.
  - `startTime`: Chunk start time in seconds (float), calculated from PCM sample count. First chunk starts at 0.00s.
  - `endTime`: Chunk end time in seconds (float), calculated from PCM sample count. Typically `startTime + ~4.0s`, but exact duration varies.
  - `duration`: Chunk duration in seconds (float), `endTime - startTime`. Typically ~4.0–4.2s. Final chunk may be < 4s if user stops recording mid-encode.
  - `blob`: MP3 encoded audio blob (binary data, `type: 'audio/mpeg'`)
  - `sizeBytes`: `blob.size` in bytes (I provide this for convenience, session-store may verify with `blob.size`)

Output I expect:
- Success: `{chunkId: string}` (unique chunk ID generated by session-store, format like `chunk_sess_20260826152037_abc123_000`)
- Failure: Error object (NOT thrown exception), one of:
  - `{error: 'session_not_found', sessionId: string}` → Session does not exist (may have been deleted, or sessionId is invalid)
  - `{error: 'quota_exceeded', usedBytes: number, capBytes: number}` → Writing this chunk would exceed storage cap
  - `{error: 'database_unavailable', reason?: string}` → IndexedDB write failed (browser storage error, permissions issue, etc.)

How I use it:
- I encode PCM buffer to MP3 blob
- I calculate chunk metadata (seq, startTime, endTime, duration, sizeBytes)
- I call `writeChunk(sessionId, chunkData)` immediately (do NOT buffer chunks in memory)
- I check return value for `error` field:
  - If success (`{chunkId: string}`):
    - I emit `chunkEncoded(sessionId, chunkId, {seq, startTime, endTime, duration, sizeBytes})` event to PWA
    - I continue recording (capture next PCM buffer, encode, writeChunk again)
  - If error (`{error: ...}`):
    - I emit `captureError(sessionId, error.error, error)` event to PWA
    - I stop capture immediately (do NOT attempt to write more chunks)
    - I mark capture as "failed" (PWA will handle user-facing error message)

### Error Handling Requirements

**`{error: 'session_not_found'}`**:

When this happens: Session was deleted between PWA's `createSession()` call and my first `writeChunk()` call, OR sessionId is invalid (typo, corrupted data, etc.)

What I do:
- Emit `captureError(sessionId, 'session_not_found')` event to PWA
- Stop capture immediately
- PWA will show error toast: "Session not found. Recording failed."

What session-store must do:
- BEFORE writing chunk, call `getSession(sessionId)` to validate session exists
- If `getSession(sessionId)` returns `null` → return `{error: 'session_not_found', sessionId}` WITHOUT writing chunk

**`{error: 'quota_exceeded', usedBytes, capBytes}`**:

When this happens: Writing this chunk would cause total storage usage to exceed user's configured storage cap (e.g., default 200 MB)

What I do:
- Emit `captureError(sessionId, 'quota_exceeded', {usedBytes, capBytes})` event to PWA
- Stop capture immediately
- PWA will:
  - Show error toast: "Storage full. Delete old sessions to free space."
  - Optionally call `enforceRetentionPolicy(capBytes)` to auto-delete oldest sessions
  - PWA may offer "Resume Recording" button after deleting sessions (calls my `startCapture` again with new sessionId)

What session-store must do:
- BEFORE writing chunk, check if `usedBytes + chunkData.sizeBytes > capBytes`
- If quota would be exceeded → return `{error: 'quota_exceeded', usedBytes, capBytes}` WITHOUT writing chunk
- Do NOT automatically enforce retention policy in `writeChunk` (that is PWA's responsibility)

**`{error: 'database_unavailable', reason}`**:

When this happens: IndexedDB write fails (browser storage permissions denied, disk full, IndexedDB corrupted, etc.)

What I do:
- Emit `captureError(sessionId, 'database_unavailable', {reason})` event to PWA
- Stop capture immediately
- PWA will show error toast: "Storage unavailable. Check browser storage permissions."

What session-store must do:
- Wrap IndexedDB write in try-catch
- If IndexedDB write throws exception → catch it, return `{error: 'database_unavailable', reason: exception.message}`
- Do NOT let exceptions propagate (I cannot catch exceptions across module boundary cleanly)

### Session Metadata Update Requirements

When `writeChunk` succeeds, session-store MUST update session metadata atomically (in same IndexedDB transaction as chunk write):

- `session.chunkCount += 1` (increment chunk count)
- `session.sizeBytes += chunkData.sizeBytes` (accumulate total session size)
- `session.duration = Math.max(session.duration || 0, chunkData.endTime)` (update session duration to latest chunk end time)
- `session.updatedAt = new Date().toISOString()` (update last modified timestamp)

Why this matters:
- PWA displays session duration in session card (reads `session.duration`)
- PWA displays session size in session card (reads `session.sizeBytes`)
- PWA displays chunk count in session detail developer mode (reads `session.chunkCount`)
- If session metadata is stale, PWA displays incorrect info to user

Session-store MUST update these fields. I do NOT call separate update functions (too slow during recording, too error-prone).

### Sequential Write Behavior

I write chunks sequentially (one at a time, NOT concurrent):
- First chunk: seq=0, startTime=0.00s, endTime=~4.12s
- Second chunk: seq=1, startTime=~4.12s, endTime=~8.24s
- Third chunk: seq=2, startTime=~8.24s, endTime=~12.36s
- ...

Session-store does NOT need to handle concurrent `writeChunk` calls for the same sessionId. I serialize writes (wait for previous `writeChunk` to return before calling next).

However, seq numbers may have gaps if encoding fails internally (e.g., seq=0, seq=1, seq=3 if seq=2 encoding was skipped due to PCM buffer corruption). Session-store MUST NOT enforce strict sequential seq (gaps are allowed).

### Chunk ID Generation Requirements

Session-store generates unique chunk IDs. I expect format like:
- `chunk_{sessionId}_{seq}` (e.g., `chunk_sess_20260826152037_abc123_000`)
- OR `chunk_{timestamp}_{random}` (e.g., `chunk_1724687437000_xyz789`)

Chunk ID MUST:
- Be unique across all chunks in all sessions
- Be stable (same chunk ID returned if I call `writeChunk` with same chunkData twice, though this should not happen in practice)
- Be sortable by seq within session (for playback-engine to assemble chunks in correct order)

I do NOT generate chunk IDs myself. Session-store owns ID generation.

### Performance Requirements

**`writeChunk` must be fast**: < 50ms per call (target), < 200ms acceptable, > 500ms causes problems

Why this matters:
- I encode chunks in a Web Worker (off main thread)
- I call `writeChunk` synchronously after encoding (await writeChunk result)
- If `writeChunk` is slow (> 500ms), PCM buffer may overflow before next encode cycle
- If PCM buffer overflows → audio data lost → gaps in recording → user hears "jumps" in playback

Optimization suggestions for session-store:
- Use IndexedDB transaction batching (write chunk + update session metadata in ONE transaction)
- Use IndexedDB indexes for fast session lookup (by-id primary key)
- Do NOT perform expensive operations in `writeChunk` (e.g., recalculating all session stats, compacting database, etc.)

### What I Do NOT Need

- I do NOT need `createSession` (PWA does that before calling my `startCapture`)
- I do NOT need `listSessions` or `getSessions` (I only write, never read)
- I do NOT need `deleteSession` (PWA does that)
- I do NOT need `getChunk` or `getChunksForSession` (playback-engine needs those, I do NOT)
- I do NOT need `writeVolumeProfile` or `writeSnip` (volume-analyzer does those)
- I do NOT need `writeTranscript` (PWA does that)
- I do NOT need `enforceRetentionPolicy` (PWA does that, NOT me)

I am a single-purpose customer: write chunks during recording. Session-store must make that FAST and RELIABLE.

### Edge Cases

**User stops recording mid-encode**:
- Final chunk may have duration < 4s (e.g., 2.3s if user stopped at 10.3s)
- I still call `writeChunk` for final chunk (same interface, just shorter duration)
- Session-store treats final chunk same as any other chunk (no special handling needed)

**Recording starts but no chunks written** (mic ghost, watchdog timeout):
- I emit `captureError(sessionId, 'mic_ghost')` or `captureError(sessionId, 'watchdog_timeout')` event
- I do NOT call `writeChunk` if no audio data captured
- Session exists but has 0 chunks (chunkCount=0, sizeBytes=0, duration=0)
- PWA may delete empty session automatically or show "No audio recorded" message

**Session deleted during recording** (user navigates away, deletes session in another tab):
- Next `writeChunk` call returns `{error: 'session_not_found'}`
- I emit `captureError(sessionId, 'session_not_found')` and stop capture
- No orphan chunks (session-store does not write chunk if session does not exist)

### Summary of Interface

| Function | Input | Output | Failure Result |
|----------|-------|--------|----------------|
| `writeChunk(sessionId, chunkData)` | sessionId (string), chunkData ({seq, startTime, endTime, duration, blob, sizeBytes}) | `{chunkId: string}` | `{error: 'session_not_found'}` OR `{error: 'quota_exceeded', usedBytes, capBytes}` OR `{error: 'database_unavailable', reason}` |

All errors returned as structured objects (NOT thrown exceptions). Session metadata updated atomically on success.
